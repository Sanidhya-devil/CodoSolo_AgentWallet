Product Requirements Document (PRD)

Phase 1 + Phase 2 — Safe AI-agent spending, containment, recovery

AgentVault | W3-02 | CodoSolo | Sanidhya Gupta

Status: Proposed specification; not a claim that features are already implemented or audited.

1. Executive Summary

AgentVault is a proposed ERC-4337-compatible smart-account wallet that lets an AI agent transact only within owner-defined policy. Phase 1 provides constrained spending authority. Phase 2 assumes the agent may be compromised and adds detection, freeze/revocation, guardian recovery, gas-sponsorship quotas, and security-invariant testing.

2. Problem and Vision

AI agents may buy API credits, tickets, services, or other goods for users. Unrestricted wallet authority is dangerous if a key is compromised, a prompt is manipulated, or an integration behaves maliciously. AgentVault aims to make the wallet enforce permissions rather than trusting the agent alone.

Vision

Give AI agents limited, auditable payment authority while keeping the owner in control before, during, and after a compromise.

3. Goals

Enforce per-transaction and daily spending caps in the smart-account authorization path.

Restrict recipients, contract targets, function selectors, agent expiry, signatures, nonces, and chain context.

Provide owner dashboard for policy, activity, approvals, alerts, freeze/revoke, and recovery.

Detect defined suspicious patterns and trigger a bounded freeze workflow.

Support 3-of-5 guardian recovery, 48-hour delay, and owner veto.

Apply per-agent gas sponsorship quotas.

Test at least five hijack scenarios and fuzz the core authorization invariant.

4. Non-Goals

Production custody of real funds during the hackathon.

Guaranteeing detection of every possible exploit or AI manipulation.

Claiming production readiness or a security audit without evidence.

Building a complex AI model; a scripted agent is sufficient for initial testing.

5. Users


| Persona | Need |
| --- | --- |
| Owner | Configure policies, inspect activity, approve exceptions, freeze/revoke and recover. |
| Agent developer | Use restricted wallet authority with clear allow/reject outcomes. |
| Guardian | Approve/reject recovery under threshold and delay rules. |
| Reviewer | Inspect tests, threat model, logs, and limitations. |


6. Scope

Phase 1 — Safe spending

Per-transaction cap and daily cap.

Allowed recipient list.

Allowed contract and function list.

Agent permission expiry.

Owner approval workflow for explicitly permitted exceptions; otherwise reject safely.

Activity history and emergency revoke/freeze.

Phase 2 — Compromise resilience

Script 5+ hijack/abuse scenarios.

Rule-based suspicious-activity detection and automatic freeze/revoke path.

Report measured detection and false-freeze rates.

Recovery with five guardians, three distinct approvals, 48-hour delay, and owner veto.

Per-agent gas sponsorship quota.

Fuzz-test invariant: funds move only via valid owner authorization, in-policy agent operation, or approved recovery.

7. Functional Requirements


| ID | Requirement | Acceptance evidence |
| --- | --- | --- |
| FR-01 | Enforce per-transaction and daily caps. | Boundary tests pass; above-cap operation rejected. |
| FR-02 | Enforce recipient allowlist. | Unknown recipient rejected. |
| FR-03 | Enforce contract/function allowlist. | Unlisted target/selector rejected. |
| FR-04 | Enforce permission expiry. | Expired agent cannot authorize operation. |
| FR-05 | Validate signatures, nonce, chain and EntryPoint context. | Invalid/replayed/wrong-context tests fail closed. |
| FR-06 | Freeze/revoke agent authority. | Subsequent agent operation rejected. |
| FR-07 | Auto-freeze defined suspicious patterns. | Threshold scenario freezes and emits event. |
| FR-08 | Require 3 of 5 distinct guardian approvals. | 2 approvals fail; 3 approvals may proceed to delay. |
| FR-09 | Enforce 48-hour recovery delay and owner veto. | Early execution fails; veto prevents recovery. |
| FR-10 | Apply per-agent sponsor quota. | Quota-exhausted sponsorship rejected. |
| FR-11 | Show policies, status, activity, approvals, recovery. | Each state visible in dashboard/demo. |
| FR-12 | Test invariant with fuzzing. | Test output retained; failures block release. |

9. Screens

Overview: policy status, spent today, daily cap, expiry, pending approvals.

Policy editor: caps, recipients, targets/selectors, expiry, anomaly thresholds and sponsor quota.

Activity timeline: allowed, blocked, approval-needed, frozen and recovery events with reason codes.

Approvals/recovery: approve/reject, guardian count, countdown and owner veto.

Emergency controls: freeze/revoke with confirmation and auditable event.

10. Security, Metrics and Risks

Fail closed on malformed or unknown authorization; do not rely on UI-only checks.

Measure detection rate and false-freeze rate on labelled scenarios; do not invent results.

Use test assets/local chain during development; real funds require independent review.

Specify daily reset semantics, guardian rotation, freeze lifting, recovery initiator and approval override rules.

Risks: policy edge cases, EntryPoint version drift, false positives, guardian unavailability/collusion, paymaster abuse. Mitigations: boundary/fuzz tests, pinned dependencies, owner veto, bounded detector permissions, quotas and review.

11. Proposed Delivery Order

Build policy engine and Foundry tests.

Add freeze/revoke and five scripted attack scenarios.

Implement recovery threshold, delay, veto and tests.

Add quota/paymaster integration or keep it as a separately scoped module if time is limited.

Build dashboard and event views; run unit, fuzz, replay, quota and recovery tests.

12. Open Decisions

Select exact ERC-4337 account, EntryPoint version and compatible bundler after verification.

Choose UTC-aligned or rolling daily spend window.

Define anomaly thresholds and freeze recovery procedure.

Define guardian identity, rotation and recovery initiator.

Define whether exceptions can ever override specific policy rules.
